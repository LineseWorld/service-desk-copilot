> 项目：Service Desk Copilot  
> 阶段目标：建立一个具备分层、依赖注入、生命周期管理、统一异常响应和自动化测试的 FastAPI 客户模块。  
> 当前结论：核心功能链路已经跑通；当前保留一个端到端客户场景测试，不要求在本阶段拆分测试函数。

## 1. 本阶段完成了什么

当前项目已经形成以下调用链：

```text
HTTP 请求
  -> FastAPI Router
  -> FastAPI Dependency
  -> CustomerService
  -> CustomerRepository 接口
  -> InMemoryCustomerRepository
  -> Domain Customer
```

发生业务错误时，调用链为：

```text
CustomerService
  -> 抛出领域异常
  -> API 全局异常处理器捕获
  -> 转换成统一 JSON 错误响应
  -> 返回 404 或 409
```

目前已经验证的行为：

| 场景 | 预期状态码 | 含义 |
|---|---:|---|
| 创建客户成功 | 201 | 已创建新资源 |
| 查询客户成功 | 200 | 请求成功 |
| 重复创建客户 | 409 | 当前资源状态发生冲突 |
| 查询不存在的客户 | 404 | 资源不存在 |
| 请求数据不合法 | 422 | 请求体未通过 Pydantic 校验 |
| 未处理的程序异常 | 500 | 服务端内部错误 |

## 3. 应用工厂：为什么使用 `create_app()`

应用工厂是一个负责创建并配置 FastAPI 实例的函数：

```python
def create_app() -> FastAPI:
    app = FastAPI(title="Service Desk Copilot", lifespan=lifespan)
    register_exception_handlers(app)
    app.include_router(customer_router)
    return app


app = create_app()
```

需要掌握：

1. `create_app()` 每调用一次，就能创建一个新的应用实例。
2. 正式启动服务时，Uvicorn 导入模块级的 `app`。
3. 测试时可以调用 `create_app()` 创建隔离的测试应用。
4. 路由、异常处理器和生命周期配置集中在这里完成。

它解决了直接在模块全局不断配置同一个 app 所带来的测试隔离和扩展困难。

代码出处：`src/service_desk/main.py`

## 4. Lifespan：应用资源什么时候创建

项目使用异步上下文管理器管理生命周期：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.customer_repository = InMemoryCustomerRepository()
    try:
        yield
    finally:
        pass
```

执行顺序：

```text
进入 lifespan
  -> 执行 yield 之前的初始化
  -> 应用开始处理请求
  -> 应用停止
  -> 执行 yield 之后的清理
```

当前在 `yield` 前创建内存 Repository。未来连接数据库、Redis、消息队列或加载 AI 模型时，也可以在这里初始化，并在 `yield` 后释放连接或资源。

需要掌握：

- `asynccontextmanager` 把含有 `yield` 的异步函数变成异步上下文管理器。
- `app.state` 用于保存应用生命周期内共享的对象。
- lifespan 管理的是应用级资源，不是为每个 HTTP 请求都重新创建资源。
- FastAPI 官方目前推荐通过 `lifespan` 处理启动和关闭逻辑。

官方资料：[FastAPI Lifespan Events](https://fastapi.tiangolo.com/advanced/events/)

代码出处：`src/service_desk/main.py`

## 5. 依赖注入：Repository 如何到达路由

依赖组装过程如下：

```text
request.app.state.customer_repository
  -> get_customer_repository()
  -> CustomerRepositoryDep
  -> get_customer_service()
  -> CustomerServiceDep
  -> customers.py 路由参数
```

典型定义：

```python
CustomerRepositoryDep = Annotated[
    CustomerRepository,
    Depends(get_customer_repository),
]

CustomerServiceDep = Annotated[
    CustomerService,
    Depends(get_customer_service),
]
```

### `Annotated` 是什么

`Annotated[T, metadata]` 表示基础类型仍然是 `T`，同时为框架附加额外信息。在这里：

```python
Annotated[CustomerService, Depends(get_customer_service)]
```

告诉类型检查器参数是 `CustomerService`，同时告诉 FastAPI 使用 `get_customer_service()` 提供这个对象。

### `cast` 是什么

`app.state` 是动态属性容器，Pylance 无法自动知道其中对象的准确类型：

```python
cast(CustomerRepository, request.app.state.customer_repository)
```

`cast` 只向静态类型检查器声明类型，不会在运行时转换或检查对象。

### 为什么路由不直接创建 Repository

如果在路由中直接写：

```python
repository = InMemoryCustomerRepository()
```

那么每次请求可能产生新的存储对象，且路由与具体实现耦合。依赖注入让路由只依赖 Service，并允许未来替换为 SQLite、PostgreSQL 或测试替身。

官方资料：

- [FastAPI Dependencies](https://fastapi.tiangolo.com/tutorial/dependencies/)
- [FastAPI Sub-dependencies](https://fastapi.tiangolo.com/tutorial/dependencies/sub-dependencies/)
- [FastAPI Classes as Dependencies](https://fastapi.tiangolo.com/tutorial/dependencies/classes-as-dependencies/)

代码出处：`src/service_desk/api/dependencies.py`

## 6. 分层：每层应该负责什么

### API / Router

负责：

- 接收路径参数和请求体；
- 调用 Service；
- 把领域对象转换成响应 Schema；
- 声明 HTTP 状态码和 OpenAPI 响应模型。

不负责核心业务规则和数据存储。

### Schema

Pydantic Schema 用于 API 边界：

- `CustomerCreate` 校验客户端请求；
- `CustomerResponse`约束服务端响应；
- `ErrorResponse` 统一错误结构。

Schema 不是领域实体。它服务于外部接口契约。

### Service

负责业务用例和规则：

- 创建客户；
- 判断客户是否重复；
- 决定客户初始状态；
- 查询客户；
- 查询失败时抛出领域异常。

Service 不应该导入 `FastAPI`、`Request`、`HTTPException` 或 API Schema。

### Domain

保存业务核心概念：

- `Customer`；
- `CustomerPlan`；
- `CustomerStatus`；
- `CustomerNotFound`；
- `CustomerAlreadyExists`。

Domain 应尽量与 Web 框架、数据库框架无关。

### Repository

接口定义 Service 所需的数据操作能力，具体实现负责真正存取数据：

```text
CustomerService -> CustomerRepository 接口
                         ^
                         |
              InMemoryCustomerRepository
```

Service 依赖抽象接口，而不是内存实现。这为以后替换数据库实现保留空间。

## 7. Pydantic：请求与响应为什么要在构造时完整

Pydantic `BaseModel` 在创建对象时执行校验。例如：

```python
CustomerResponse()
```

如果 `id`、`name`、`plan`、`products` 是必填字段，就会立即产生 `ValidationError`。不能按照普通可变对象的思路先空构造再补字段。

正确思路是一次性提供完整数据：

```python
CustomerResponse(
    id=customer.id,
    name=customer.name,
    plan=customer.plan,
    status=customer.status,
    products=customer.products,
)
```

### `json=` 与 `content=`

测试 JSON API 时推荐：

```python
client.post(url, json=payload)
```

`json=` 会序列化 Python 对象并设置 JSON Content-Type。`content=` 代表原始请求体，使用它时需要自己保证编码、JSON格式和请求头正确。

### `model_dump()`

`ErrorResponse` 是 Pydantic 对象，而 `JSONResponse(content=...)` 需要可序列化内容，因此可以使用：

```python
error.model_dump()
```

把模型导出为字典。

官方资料：[Pydantic Models](https://docs.pydantic.dev/latest/concepts/models/)

- `src/service_desk/schemas/customer.py`
- `src/service_desk/schemas/error.py`

## 8. 统一异常处理：为什么 Service 不返回 HTTP 错误

Service 表达业务事实：

```python
raise CustomerNotFound(customer_id)
```

API 层决定这个事实如何映射到 HTTP：

```text
CustomerNotFound       -> 404 Not Found
CustomerAlreadyExists  -> 409 Conflict
```

这种设计使 Service 可以被 HTTP API、命令行、后台任务或未来的 AI Agent Tool 复用，而不绑定 FastAPI。

异常处理器返回统一结构：

```json
{
  "code": "customer_not_found",
  "message": "Customer 'customer-001' was not found"
}
```

`code` 是稳定、便于程序判断的机器码；`message` 是面向人阅读的信息。

为什么未注册处理器时返回 500：自定义领域异常只是普通 Python 异常。FastAPI 不知道它对应哪个 HTTP 状态码，未处理异常因此成为服务端内部错误。注册异常处理器后，它才会转换成 404 或 409。

官方资料：[FastAPI Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/)

代码出处：

- `src/service_desk/domain/exceptions.py`
- `src/service_desk/api/errors.py`
- `src/service_desk/main.py`

## 9. pytest、fixture 与 TestClient 生命周期

测试 fixture：

```python
@pytest.fixture
def client():
    app = create_app()

    with TestClient(app) as test_client:
        yield test_client
```

### 为什么使用 `with TestClient(app)`

上下文管理器会触发应用 lifespan：

```text
进入 with
  -> lifespan 启动
  -> Repository 创建
  -> 执行测试请求
离开 with
  -> lifespan 清理
```

只创建 `TestClient(app)` 而不进入上下文时，不应依赖 lifespan 一定被执行。

### fixture 默认作用域

没有指定 `scope` 时，pytest fixture 默认是 `function`：每个测试函数获得一个新 fixture 实例。因此，不同测试函数默认不共享 app 和内存 Repository；同一个测试函数内通过同一个 client 发送的多个请求会共享当前 app 和 Repository。

### 本项目当前测试取舍

当前客户 API 的创建、查询、重复创建和缺失查询保留在一个完整场景测试中。这样可以连续验证同一个应用生命周期内的状态变化。你已经理解测试隔离，本阶段不要求拆成四个测试。

需要清楚这一取舍：如果前面的断言失败，后续步骤不会继续执行，pytest 也只会报告一个测试场景。未来测试规模扩大时，可再按业务行为拆分。

### 为什么出现大量 `.venv` 调用栈

`TestClient` 默认使用 `raise_server_exceptions=True`。未处理异常会被重新抛给 pytest，调用栈会经过 HTTPX、Starlette、FastAPI 和 AnyIO，所以会看到大量 `.venv/Lib/site-packages` 路径。阅读时通常从调用栈最底部向上找第一个项目代码位置和最终异常。

不建议为了隐藏错误而关闭 `raise_server_exceptions`。正确做法是处理预期的业务异常，让真正的程序错误继续使测试失败。

- [FastAPI Testing](https://fastapi.tiangolo.com/tutorial/testing/)

- [FastAPI TestClient Reference](https://fastapi.tiangolo.com/reference/testclient/)

## 10. `src` 布局、构建系统与 uv

项目使用：

```text
service-desk-copilot/
  pyproject.toml
  src/
    service_desk/
  tests/
```

`src` 是源码根目录，不是 Python 包名。正确导入是：

```python
import service_desk
```

而不是：

```python
import src.service_desk
```

`pyproject.toml` 中的 `[build-system]` 告诉 uv 当前项目需要被构建和安装。由于发行项目名是 `service-desk-copilot`，实际 Python 模块名是 `service_desk`，项目使用 `module-name` 明确二者的对应关系。

常用命令：

```powershell
uv sync
uv run python -c "import service_desk; print(service_desk.__file__)"
uv run uvicorn service_desk.main:app --reload
uv run pytest
```

命令含义：

- `uv sync`：根据项目配置同步虚拟环境和依赖，并安装当前项目；
- `uv run`：在项目环境中执行后续命令；
- `python -c`：直接执行一段短 Python 代码；
- 打印 `service_desk.__file__`：确认实际导入的是当前项目源码。

## 11. Ruff：检查和格式化不是同一件事

```powershell
uv run ruff check .
```

执行静态规则检查，例如：

- 未定义名称；
- 未使用导入；
- 导入顺序；
- 潜在错误；
- 项目启用的风格规则。

自动修复可安全修复的问题：

```powershell
uv run ruff check . --fix
```

格式化代码：

```powershell
uv run ruff format .
```

只检查格式、不写文件：

```powershell
uv run ruff format . --check
```

Ruff formatter 不负责排序导入，因此通常先运行 linter fix，再运行 formatter。

推荐验证顺序：

```powershell
uv run ruff check . --fix
uv run ruff format .
uv run ruff check .
uv run ruff format . --check
uv run pytest
```

官方资料：

- [Ruff Linter](https://docs.astral.sh/ruff/linter/)
- [Ruff Formatter](https://docs.astral.sh/ruff/formatter/)
- [Ruff Configuration](https://docs.astral.sh/ruff/configuration/)

## 12. 本阶段必须能够回答的问题

### 为什么使用应用工厂？

为了集中组装应用，并允许正式运行和测试分别创建应用实例，提高隔离性和可配置性。

### 为什么 Repository 放在 `app.state`？

当前 Repository 是应用级共享资源，由 lifespan 创建，并供请求依赖读取。未来数据库连接池等应用级资源也可以使用类似方式管理。

### 为什么 Router 持有 Service，而不是直接持有 Repository？

Router 负责 HTTP，Service 负责业务用例。让 Router 直接操作 Repository 会绕过业务规则，并导致业务逻辑散落在接口代码中。

### 为什么 Service 接收业务字段而不是 `CustomerCreate`？

`CustomerCreate` 是 API 输入 Schema。Service 接收 `customer_id`、`name`、`plan`、`products` 等业务字段，可以脱离 FastAPI 和 Pydantic 被其他入口复用。

### 参数很多是否合理？

少量、明确且属于同一业务命令的关键字参数是合理的。参数明显增多或形成稳定业务概念时，再引入业务命令对象或值对象，不需要为了减少参数而让 Service 依赖 API Schema。

### 为什么请求不合法返回 422？

请求已经匹配到路由，但请求体不能构造成声明的 Pydantic 输入模型。FastAPI 在进入路由函数前完成校验并返回 422。

### 为什么领域异常未处理时返回 500？

FastAPI 不知道自定义 Python 异常对应哪个 HTTP 状态码。通过 API 层注册异常处理器后，才能稳定映射为 404 或 409。

### 为什么测试使用 `json=payload`？

它会把 Python 对象序列化成 JSON 并设置正确的 Content-Type；`content=` 只是发送原始请求体。

### 为什么测试使用 `with TestClient(app)`？

为了确保应用的 lifespan 启动和关闭逻辑在测试中实际执行。

### 为什么不同测试通常不共享数据？

默认 function scope fixture 会为每个测试函数重新创建 app 和内存 Repository。这样测试不依赖执行顺序，也不被其他测试污染。
